# Ti60 FPGA 轻量 CNN 识别试验版

交付日期：2026 年 10 月 30 日。器件为 Ti60F225，时序模型 I3，使用 Efinity 2026.1.132 构建。

本工程已经生成可下载的 bit 文件和用于 Flash 的 hex 文件，完成 RTL 仿真、综合、接口生成与布局布线。本次没有连接或烧写开发板。板上摄像头图像、HDMI 实际输出和断电启动仍需要实物验证。

## 识别范围

当前使用之前已经训练完成的 938 参数 CNN，判断取景框中的脸部是否匹配所给的护目镜人物图案。输出分为目标图案与其他画面两类。训练中的另外三张表情图属于负样本，不能输出它们各自的表情名称。此版本没有自动寻找人脸，也不保证识别同一角色的任意画法或表情。

本次复用了既有 200 轮 CPU 训练所得权重，没有重新训练，也没有新增生成图片。29 个现有开发样本的量化分类与浮点模型一致。其组成是 16 个训练样本、4 个同源验证样本和 9 个人工裁切、透视校正的手机照片脸部区域。照片用于过预处理诊断，不是直接从 FPGA 摄像头读取的原始帧，29/29 不能作为实际摄像头识别准确率。

## 使用烧录文件

| 文件 | 用途 |
| --- | --- |
| `outflow_cnn/ti60f225_oob.bit` | JTAG 临时下载，断电后不保留 |
| `outflow_cnn/ti60f225_oob.hex` | 通过 JTAG-SPI 桥写入板上 Flash，断电后保留 |
| `outflow_cnn/cnn_verification.json` | 本次构建的资源、时序、测试范围及文件 SHA256 |
| `program_cnn.ps1` | 明确执行时才连接并下载；构建脚本不会调用它 |

在 Efinity Programmer 中，临时测试使用 JTAG 模式和 bit 文件。Flash 文件需要 JTAG-SPI 桥方式，不能把 hex 当成 JTAG bit 文件直接下载。交付脚本沿用原工程的 Ti60 桥镜像 `u10660A79.bit`，先加载桥，再擦写并校验 Flash，最后加载应用 bit 使程序立即运行。

以下命令只在用户主动运行时才会烧写，交付过程没有执行：

```powershell
powershell -ExecutionPolicy Bypass -File .\program_cnn.ps1 -Mode Jtag
powershell -ExecutionPolicy Bypass -File .\program_cnn.ps1 -Mode Flash
```

默认 Efinity 安装位置为 `D:\efinity\2026.1`。其他电脑通过 `-EfinityHome` 指定安装路径。脚本先验证 bit、hex 与构建记录的哈希一致。Flash 写入成功与断电重启成功是两项不同的板级检查。

## 按键和画面

| 按键 | 功能 |
| --- | --- |
| SW0 | 原工程复位，重新初始化视频链路 |
| SW1 短按 | 边缘阈值增加 8；双帧回放模式中选择回放帧 |
| SW2 短按 | 边缘阈值减少 8；双帧回放模式中选择回放帧 |
| SW3 短按后松开 | 依次切换四种显示模式 |
| SW3 按住约 1 秒 | 普通模式冻结或恢复；快照、回放模式重新锁定画面 |

开机为模式 0，显示灰度与边缘对照。短按 SW3 一次进入模式 1，显示彩色画面、红色边缘和 CNN 取景框。再次短按进入模式 2 同帧快照，再次短按进入模式 3 双帧回放，再次短按回到模式 0。回放是两个已完成帧之间切换，不是录制一段视频。

CNN 只在模式 1 工作。画面顶部显示 `CNN WAIT` 表示尚未得到结果；`CNN OTHER` 表示未满足目标匹配；`CNN TARGET` 表示连续三个有效结果均匹配目标。对应取景框依次为黄色、红色、绿色。分类分数是内部整数 logit，不显示为概率。

1920×1080 画面中的取景框左上角为 (704, 412)，大小为 512×256。需要让目标的完整脸部落在框内，眼睛和嘴都进入框中，接近随包测试图 `cnn/reference/photo_checks/01_tablet_face.png` 的范围。只把一只眼睛或额头放入框中，不能按完整脸部输入判断。取景框位置固定，不会跟随人物移动。

## 硬件实现

识别支路取原工程灰度流，在取景框内按 16×8 像素块求均值，生成 32×32 输入。随后按每幅输入的最小值、最大值完成整数归一化；灰度跨度小于 16 的平坦画面直接按无效输入处理。软件训练的 BOX 缩放与 RTL 整数块均值存在舍入方式的区别，真实 ISP、曝光与拍屏变化也可能影响结果，这些因素仍需实拍验证。

CNN 结构为 3×3 卷积 1→4、ReLU、2×2 最大池化，随后为卷积 4→8、ReLU、最大池化，再接卷积 8→8、ReLU、全局平均及 8→2 全连接。权重为有符号 8 bit，激活为无符号 8 bit，偏置和累加使用 32 bit。卷积与池化合并遍历，共用计算单元，避免保存完整的 32×32×4 中间特征。

两个激活存储区共 2048 字节，916 个量化权重放在 ROM 中。最终综合结果中 CNN 识别模块占 3 个内存块、2 个 DSP。区域累加使用寄存器。计算期间不接收下一幅输入，视频主链继续运行；不完整采样不会启动推理，计算期间到来的帧同步不会打断当前推理。结果与取景框状态在显示帧边界更新。

现有摄像头寄存器表、MIPI 输入、DDR3 帧缓存、ISP、HDMI 和按键引脚约束均沿用基础工程。本次没有移植 OV5640 DVP 接口，也没有更换引脚。Canny 处理网格保留 640×480，采集和显示链路沿用 1920×1080。CNN 输入的 32×32 是独立识别支路，不是将基础边缘检测分辨率降为 32×32。

## 工程入口与复现

在 Efinity 中打开 `ti60f225_oob.xml`，器件选 Ti60F225，Timing Model 使用 I3。完整构建入口是 `build_cnn.ps1`，输出到 `outflow_cnn`。原模板匹配 RTL 保留用于历史回归，实际顶层启用 `CNN_ENABLE=1`，关闭 `EXPRESSION_ENABLE`，不会同时占用两套识别器的内存。

```powershell
powershell -ExecutionPolicy Bypass -File .\build_cnn.ps1 -PythonExe "你的Python路径"
```

构建测试需要 Python、NumPy、Pillow；Icarus 仿真器随包提供。仅重新构建 RTL 不需要安装 PyTorch。重新导出量化参数时使用 `cnn/export_model.py`，需要 PyTorch 2.9.1、NumPy 和 Pillow。导出程序只使用随包的 checkpoint 与参考样本，不依赖原电脑微信目录。修改模型后必须重新导出、仿真和构建，不能只替换模型 pt 文件后继续使用旧 bit。

`cnn/reference` 保存模型定义、预处理、原训练脚本及训练数据与历史训练报告。历史报告中的未部署状态对应当时的软件阶段；当前 RTL、资源与构建状态以 `outflow_cnn/cnn_verification.json` 为准。原文件中的项目背景说明不等于本次板级测试记录。

GitHub 参考项目为 <https://github.com/omarelhedaby/CNN-FPGA>，核对的提交为 `0baf51a88c8fb8d55207ef4931a9a66c4a2c847a`。其网络、激活函数和目标平台不同，本次没有直接复制其整网 RTL，也没有使用其 MNIST 权重；识别逻辑按当前小模型重新实现。

本交付属于可烧录的 CNN 试验版。它证明当前模型已转换为 FPGA 逻辑并通过所列构建与仿真，不证明新场景、未知图案或实际拍摄条件下的识别可靠性。
